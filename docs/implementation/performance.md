# Rust / Svelte 性能验收

本报告引用 `benchmarks/implementation/results/` 的本次原始结果；
`benchmarks/refactor/results/` 是保留的原始评估，不被覆盖。输入均为合成数据，
没有读取用户日志进行 benchmark。Linux/WSL 结果不能代替 Windows/macOS 性能。

## 方法与边界

本机为 WSL2 x86_64、Python 3.14.4、Rust 1.96.0、Chromium 148。
核心、索引、服务采用顺序独立进程，release 构建；每项 2 次预热、15 个样本。
OS 文件缓存为 warm；“cold”表示没有应用解析缓存，**不是**丢弃 OS page cache。
内存为完整 worker 的峰值 RSS（KiB），不把某一函数的分配量当作进程内存。
索引负载为 160 文件 × 80 事件；远端恢复为 10,000 个旧版摘要（无详情）。
原始输入生成器、工具版本、样本和制品/源哈希随结果保存。

浏览器负载为 10,000 远端会话加 1 个本地会话；本地追加后有 10,004 个事件。
延迟从页面内派发 input/click 到新 DOM 可见、强制布局并经过一次绘制帧，
包含真实 HTTP、后端查询、JSON 解码及 DOM 工作；不包含 Playwright 自动点击等待。
详情每次重新请求，保留完整图表，事件表为 100 行。项目展开包括首次请求和后续
已有页面数据的复用；原始样本保留，不能推广为任意冷启动项目的延迟。

阶段 1 的 Python 页面实验另在 `stage1.json`：它只测 DOM/布局，不包含 HTTP。
长详情 P95 从 1766.1 ms 降为 17.8 ms；项目展开从 110.8 降为 25.5 ms；
代理展开从 101.9 降为 13.1 ms。搜索为 81.5/86.3 ms，没有声称该阶段改善搜索尾延迟。
这些主要来自分页、搜索索引和局部更新，不能标为 Rust 或 Svelte 框架速度收益。

## 挂载盘库存退化及修复

首轮完整服务基准暴露了 2,000 个历史文件的退化：Python 缓存命中约 3.1 ms，
Rust 每轮约 3.1 s；Rust 的 34,000 次 metadata 检查和 0 次历史缓存命中直接表明缓存未生效。
原始证据保存在 `server-performance-before-inventory-fix.json`。

原因是完整扫描超过两秒 TTL，而缓存时刻记录在扫描开始；扫描结束即过期，后续轮次一直全查。
修复将**实际检查过的文件**的缓存窗口起点放到本轮完成，缓存命中不会延长过期时间。
watcher 提示仍立即失效，过期后仍重新检查。新增测试验证“命中不续期、过期重查、提示失效”。
历史文件可见延迟包含两秒缓存窗口、扫描和后台轮询成本，不承诺两秒以内端到端可见。

另用同一挂载目录比较了 Python stat、Rust metadata/libc stat/fstatat；并未发现足以解释
千倍 warm 退化的系统调用差异，生产继续使用标准 metadata。诊断探针保留在
`metadata_probe.rs`，单次数据在 `metadata-diagnostic.json`，不把单次探针当作发布 benchmark。

## 完整服务、库存与常驻开销

启动时间包括进程启动、索引构建/恢复、第一个旧版列表 HTTP 响应与解码。

| 场景 | Python P50 / P95 ms | Rust P50 / P95 ms |
| --- | ---: | ---: |
| 首次列表 | 543.93 / 550.92 | 131.33 / 133.82 |
| 重启缓存恢复 | 342.97 / 353.53 | 84.31 / 87.74 |
| 原生目录 2k 历史文件库存 | 2.58 / 3.44 | 1.87 / 2.41 |
| WSL 挂载盘 2k 历史文件缓存命中 | 3.19 / 5.01 | 3.54 / 4.29 |

修复后的挂载盘样本记录 2,000 次实际 metadata 检查和 32,000 次缓存命中；
P50 差异约 0.35 ms，保留毫秒级 warm 路径。

无浏览器客户端、160 文件不变的 300 秒空闲运行：CPU 累计 0.09 秒，
RSS 增长 28 KiB，句柄增长 0；完整解析计数保持 160、revision 不变。
采样点每 10 秒记录在 `server-performance.json`，不从单次延迟推断常驻占用。

这轮服务/空闲报告来自库存修复后、一次性 CLI 临时索引调整前的构建，build ID 在原始 JSON 中；
后续 CLI 调整不改变常驻服务的索引和查询路径，并另经并存导出集成测试验证。
交接前另修复了旧价格分段缺字段的兼容解析，并将递归监听从整个 Codex 目录缩到日志目录；
修复后差分、HTTP 和实际浏览器回归重新通过。性能文件保留各自受测构建/制品哈希，
不把先前采样伪写成最终二进制的新采样；`final-health.json` 记录实际交接构建。

## 验收范围

- 计数、费用、身份、事件集合的正确性门禁通过；内存门禁通过。
- 无变化查询保留 204/no-render；WSL 历史缓存退化已修复，旧失败数据保留。
- 长详情、10k 搜索/展开延迟门禁通过；完整事件分页/导出另经 HTTP 精确比较。
- 并发覆盖四客户端、活跃日志追加与远端导入；未发现重复、丢失或跨 revision 混合。
- 解析、时间线、价格查询/分段分别计时；关系归一化、期间/日历、汇总及持久化的组合成本计入索引/View 和 HTTP。
  Git/runtime tier、各个单独查询没有逐一隔离测速，不对这些模块宣称单独倍数；远端 HTTP 导入仅有功能/并发验收，恢复/合并有独立计时。
- 原生 Windows 21 项核心测试通过，但完整性能/安装/浏览器门禁仍未通过；macOS 尚未运行。
  本次不宣称全平台发布就绪，也不推算未来 Tauri 客户端的收益。
