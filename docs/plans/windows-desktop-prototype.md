## 目标

在现有 Rust + Svelte 项目上同步实现 Windows、macOS、Linux 桌面客户端，共用统计核心、界面与大部分应用逻辑，按平台适配并交付各自的安装、日常使用和升级体验。优先保证安装顺畅、启动可靠、统计准确、界面响应、文件操作自然、数据安全和设置持久化。原型是中间里程碑，不是整个计划的完成标准。

计划覆盖三端运行基础、桌面原型、安装与日常使用、更新与平台发布验证。从第一个原型就覆盖三端，不能先完成 Windows 全部功能，再把 macOS/Linux 留作未实施的后续工作。按阶段执行和验收，不表示后面的客户端能力不实施。公开发布、购买证书和其他外部操作仍需用户授权或提供相应资源。

Agensi 是将来可选的分发/调用渠道。只保留通用的本地自动化能力，不将其交付条款、收费规则、账号体系或技术限制变成客户端的产品约束。

## 产品优先级与决策原则

1. 客户端独立好用：用户不需要知道 Skill、Agent、MCP、后台端口或实例记录，就能完成安装、查看用量、导入导出和更新。
2. 优先复用统计与界面；根据桌面体验和维护成本决定通信与进程结构。
3. 保留清晰的内部边界和已有 CLI；新增自动化接口服务于本地工具生态，可被任何 Agent 或脚本使用。
4. 最后单独适配 Agensi；平台不接受某种安装或收费方式时，调整适配层、缩小平台承诺或放弃该渠道，不牺牲客户端体验和独立分发能力。

不能为了接入 Agensi，让客户端每次联网加载 Skill、要求平台登录、依赖平台付费状态、暴露底层配置，或限制客户端自己的升级与商业模式。

## 平台交付矩阵

首批目标沿用现有原生后端支持的四种架构，避免桌面壳支持某架构但随包后台程序缺失：

| 桌面端 | 首批架构 | 交付形式 | 平台重点 |
| --- | --- | --- | --- |
| Windows | x64 | 每用户安装的 `.exe` 安装包 | WebView2、开始菜单、托盘、应用签名、运行中程序替换 |
| macOS | Apple Silicon arm64、Intel x64 | 各架构 `.app` / `.dmg`，先不强求 Universal 合包 | WKWebView、应用菜单/Dock、应用包内资源、签名和公证 |
| Linux | x64，glibc | AppImage + Debian/Ubuntu `.deb` | WebKitGTK、系统依赖、X11/Wayland、桌面入口和托盘兼容 |

- 三个平台共享一个桌面项目；平台相关路径、启动、激活、退出、菜单、文件对话框和更新行为封装在适配层，不复制三套统计与前端。
- 默认系统范围为 Windows 10/11、Linux Ubuntu 22.04 / Debian 12 起的已验证环境；macOS 最低支持版本在冻结 Tauri/前端依赖后按所需 WebKit 功能和运行验证确认，不能把 CI runner 的版本当作最低支持承诺。实施早期必须记录正式支持表。
- 上述架构和 Linux 发行版是明确的首批支持范围，不自动扩展为 Windows ARM、Linux ARM、Alpine/musl 或所有 Linux 桌面环境；扩展不阻塞三端首批交付。
- 基础功能与数据结果一致，系统行为遵从各平台习惯。例如 macOS 关闭窗口与退出应用的区别，不强行复制 Windows 的关闭语义。
- 平台能力不等价时提供正常可用的替代操作；例如 Linux 桌面没有托盘时，不能让窗口隐藏后无法恢复。

Tauri 三端使用不同 WebView；相同网页构建通过不代表三端显示和交互都通过。参考 [WebView 平台说明](https://v2.tauri.app/reference/webview-versions/) 和 [Linux 打包基线](https://v2.tauri.app/distribute/appimage/)。

## 架构决定

默认采用 Tauri 2 桌面宿主，随客户端交付现有 Rust 服务二进制作为辅助进程；先让桌面窗口加载已经验证身份的本机服务页面，继续使用现有 Svelte 界面及 HTTP/SSE。这是基于现有代码的实施起点，不是 Agensi 对客户端的要求。

在原型里验证启动性能、文件操作、进程退出和故障恢复；如果证据表明进程内 Rust 服务、打包页面或少量原生 IPC 更适合客户端，可调整实现。保留共享领域逻辑与通用自动化接口即可，不要求为了 Agent 永久保留 HTTP 或独立常驻服务。

```text
用户点击应用
          ↓
Tauri 桌面宿主（窗口、单实例、托盘、更新）
          ↓
Svelte 界面 ── HTTP / SSE ── Rust 服务 ── usage-core
                                   ↑
                         本地查询与导出命令
                                   ↑
                  脚本 / 各类 Agent / 可选 Agensi 适配
```

- 统计逻辑不复制到桌面宿主中，首版不全面迁移为 Tauri invoke。
- CLI 与桌面共用同一个实例管理实现，可抽取共享 Rust 模块或 crate，避免两套锁、身份校验和进程发现代码。
- 桌面宿主能够从构建输出或随包资源定位确定的服务二进制；使用前检查其版本与 build ID，不能从任意 PATH 静默执行同名文件。
- 明确前端资源由服务提供；桌面原型不再分发另一份可能与后端不匹配的看板资源。
- 原型启动与正常使用不要求终端用户安装 Node、Python 或 Rust；这些仍可作为开发依赖。

## 阶段一：运行基础

### 1. 目录和实例记录

- 建立统一的路径解析入口，区分安装资源、用户数据、可重建缓存和运行状态。
- 保留已有 `cousash` 业务数据、设备身份和导入快照的兼容性；本阶段不强制迁移或删除旧目录。
- 保留 `COUSASH_CONFIG_DIR` 的显式隔离语义，正式运行、开发工作树和测试实例各自独立。
- 实例记录至少包含：记录 schema 版本、实际 loopback 地址、PID、随机 instance ID、服务版本、build ID、协议版本及所属配置范围。
- 记录中涉及控制令牌的内容只能存放在受当前用户保护的文件中，不能进入常规 JSON 输出、前端、URL、截图或提交。
- 原子写入记录；使用有界等待的启动锁，避免并发启动出多个索引写入者。
- 发现记录后必须核对健康状态与身份；残留记录、PID 重用、无效记录、启动中、服务已退出都要有明确处理。
- 如果兼容旧 `launcher-process.json`，必须验证旧记录和服务身份后使用，不能把任意占用 8765 的监听者接管为本应用。

### 2. 端口和启动协议

- 桌面原型支持自动选择可用本机端口，可使用 `127.0.0.1:0`；实际端口以成功绑定的 listener 为准。
- 服务通过受保护的准备就绪记录或有结构的握手返回实际地址；不要从杂乱日志中解析 URL，也不要先释放探测端口再启动以制造竞争。
- 普通启动、桌面和新 CLI 命令优先发现同配置范围的已有兼容实例。
- 共享启动协议不得依赖 Windows 命令行或 `.exe` 扩展名；macOS/Linux 从 Finder、Dock、桌面菜单启动时可能不继承终端 PATH，资源和后台程序必须从确定的应用位置解析。
- 保持已有入口可用；对默认 8765 行为的兼容和桌面自动端口行为作明确区分并写入文档。
- 配置范围、来源、协议或版本不匹配时给出可操作的冲突信息；仅在确认归属且符合更新/重启规则时替换实例，不能停止其他工作树或未知服务。
- 启动超时、索引失败和服务异常退出应返回错误及日志位置；失败启动应清理本次拥有的状态，不能留下失控子进程。
- 不在 UI 主线程执行长时间启动或索引等待。

### 3. 本地命令接口

先保留已有 CLI 和可复用的应用操作入口；新增命令在桌面核心体验验证后完善，不作为展示真实客户端前的前置条件。接口面向通用本地自动化，可根据 clap 兼容性调整拼写，并记录最终协议：

```text
codex-usage-dashboard open [--json]
codex-usage-dashboard status --json
codex-usage-dashboard summary --period today --json
codex-usage-dashboard export --output <path> [--redact] [--json]
```

- `open`：打开或聚焦桌面原型，不重复启动窗口或服务。没有桌面程序时明确返回 `desktop_not_installed` 一类错误，不能假装成功。
- `status`：无副作用，不为查询状态启动窗口或索引；区分 stopped、starting、ready、error。
- `summary`：优先复用运行中的索引，支持明确时间范围，使用应用选定展示时区进行日期边界计算。没有服务时可按文档约定启动无窗口服务或执行一次性查询；不能忽略该状态。
- `export`：有服务时优先复用，输出路径必须明确解析；支持脱敏导出，并保留原有快照格式与完整导出能力。失败不应破坏已有目标文件。
- JSON 使用版本化结构，包括成功/失败、数据或稳定错误代码。正常输出只含 JSON；诊断和进度走 stderr，不打印控制令牌。
- 规定退出码、超时以及不兼容协议行为；保留已有 `--build-info`、`--once --json`、`--export-snapshot`、`--stop` 等兼容入口。
- 单纯查询统计无需打开桌面窗口。

### 4. 应用设置持久化

- 将语言、展示时区等长期设置存入应用配置，服务、桌面和 Agent 使用同一份设置。
- 动态端口变化、关闭重开及版本升级后设置仍可恢复；临时筛选、项目展开等页面状态可继续放在前端。
- 旧 localStorage 可以作为首次迁移来源，但不能覆盖已经存在的应用配置；不同浏览器的数据无法直接跨进程读取，不承诺自动找回不可访问的旧浏览器设置。
- 设置读取、校验、原子保存及失败提示应有明确实现；避免 UI 显示已保存而写入实际失败。
- 保持现有安全层；如果新增设置 API，写请求同样经过 token 和来源检查。

## 阶段二：三端桌面原型

### 5. Tauri 宿主与窗口

- 增加独立的桌面 crate/目录和构建入口；不要让现有纯命令行发布必须安装桌面依赖才能使用。
- 从最小窗口阶段就接入 Windows x64、macOS arm64/x64、Linux x64 构建矩阵，验证各架构随包服务能启动；不能把仅 Windows 编译通过作为三端原型完成。
- 原型能通过构建产物直接运行，自动定位同版本的服务，显示真实看板，而不是打开系统浏览器。
- 使用正常系统标题栏和菜单，按平台支持最小化、最大化/全屏、缩放和关闭；首版复用现有视觉设计，并采用各平台熟悉的快捷键。
- 服务准备期间提供清楚的加载状态；索引失败或进程退出提供错误和重试入口，不能一直白屏或永久 loading。
- 同一配置范围重复启动聚焦已有窗口；不同开发配置范围不错误地聚焦另一工作树窗口。若 Tauri 插件无法直接按配置范围隔离，应实现相应的宿主发现/激活机制。
- 原型阶段实现各平台正常的窗口关闭与明确退出：Windows/Linux 可默认关闭退出；macOS 区分关闭窗口与退出应用，支持 Dock 再次显示窗口及 Cmd+Q 退出。在阶段三完善托盘/菜单栏和可选开机启动，完成整个三端客户端计划时不能只停在原型行为。

### 6. 生命周期和本机边界

- 记录桌面和服务的归属关系。关闭桌面时仅正常停止其拥有的服务；若连接的是已有独立后台服务，应按明确的所有权规则保留，避免意外关闭 CLI 启动的任务。
- CLI 的 open 能通过单实例转发或本机控制通道聚焦窗口；调用后有界返回，不因继承输出管道而挂住。
- 桌面崩溃、服务崩溃和再次启动不能导致永久锁或端口泄漏；提供可恢复流程并验证。
- macOS 的再次激活/Dock 点击、Linux 桌面会话与单实例机制都应纳入验证；不能仅依赖 Windows 命名对象或假定所有平台存在相同的系统 IPC 环境。
- 继续只绑定 loopback，保留主线 Host/Origin/Fetch Metadata 与写 token 检查。不能为了让 WebView 工作而开放任意 Origin 或公网监听。
- Tauri 的原生能力只给确认归属的应用页面；外部页面不能获得任意文件、shell 或进程权限。窗口导航限制在可信应用地址，外部链接按明确允许的协议交给系统浏览器。
- 不把长期控制令牌放入 URL、前端 JavaScript 或常规状态响应。

### 7. 现有功能在 WebView 中的兼容

- 真实验证概览、项目列表、主会话/子代理详情、筛选、日历、图表和 SSE 更新。
- 导入本地 `.json` / `.json.gz` 快照、重命名和导出必须实际可用。若现有浏览器文件选择或下载方式不兼容 WebView，应实现最小必要的原生适配；不能将功能损坏直接留待安装器阶段。
- 保留最新设备数据结构：导入是清晰的主要操作；本机卡片始终有完整/脱敏导出；没有远端快照时只显示远端空状态，不能隐藏本机操作或误报没有本机数据。
- 保持脱敏导出和完整导出的区分，以及共享提示框中的数据范围说明、真实导出进度和忙碌/禁用状态；不恢复旧版按钮旁重复的次级说明。
- 设置页已移除强制刷新按钮，迁移时不要按旧代码或截图补回；必要的刷新/恢复能力保留在内部接口或明确的故障恢复流程中，不因此重新增加常驻操作。
- 网页内提示使用 `data-tooltip` / `openTooltip` 和 `web/src/tooltip.css`；不恢复图表独立浮层样式，不加原生 HTML `title`。普通控件提示锚定目标上方、空间不足翻到下方；侧栏提示在右侧；图表鼠标读数跟随指针，键盘读数锚定数据点。
- 提示框须与键盘焦点共享内容并通过 `aria-describedby` 关联；支持离开、失焦、Escape、点击、滚动和缩放关闭，Escape 先关闭提示再关闭外层面板。必须验证模态弹窗内和顶层浮层中的显示、不裁切与视口边界间距，以最新 UI 契约为准。
- 三端 WebView 验收包含共享提示框依赖的 Popover/顶层显示能力，以及 `Intl.supportedValuesOf`、日期时间格式化等现有页面能力；在最低支持系统上验证，不以某个 Chromium 版本的通过推断 WKWebView/WebKitGTK 可用。必要兼容处理集中在共享层，不能退回多套提示框样式。
- 验证语言、时区、窗口尺寸变化和键盘操作；日期时间展示遵守仓库约定。
- 分别验证三个系统的本地 Codex 来源、用户目录及权限；同一份虚构日志在三端产生一致统计。Windows 上现有 WSL 自动发现主要是 WSL → Windows，不能未经验证宣称 Windows 客户端已自动合并所有 WSL 日志。

## 阶段三：安装与日常使用

### 8. 安装、首次启动与卸载

- 按交付矩阵生成三端可分发包：Windows 每用户安装和开始菜单入口，macOS `.dmg` 拖入 Applications，Linux AppImage 和 `.deb` 桌面入口；安装后从对应系统入口正常打开。
- Windows 自动检查并处理 WebView2；macOS 按声明的系统版本验证 WKWebView；Linux 通过包依赖或 AppImage 打包策略处理 WebKitGTK 及所需库。明确在线/离线和系统依赖范围，不能把桌面运行库误称为开发工具，也不能要求终端用户安装 Node/Rust。
- Linux 在声明的最旧支持构建基线上打包，验证目标 glibc 和 WebKitGTK 依赖；不能在新系统编译后仅凭 AppImage 格式宣称兼容所有旧系统。
- macOS 验证应用被移动到 Applications 后后台资源定位、首次打开和重复激活；Linux 验证 AppImage 移动后的资源定位，以及 `.deb` 的标准安装、升级和移除路径。
- 从任意工作目录点击应用均能正确找到资源和后台程序；安装到含空格及中文的路径也应工作。
- 首次启动自动发现默认 Codex 日志；未找到、目录无权限或需要自定义来源时，给出清楚的空状态和文件夹选择，不显示虚假的零用量成功状态。
- 设置中可查看和修改本机日志来源。首版必须可靠支持三端各自的本地来源；对 WSL 来源按实际验证结果提供支持或明确限制。
- 通过标准文件对话框导入和导出，记住合适的默认目录；取消、同名覆盖、无写权限、大快照和失败重试都有明确行为。
- 覆盖安装和卸载先协调退出本应用进程，不影响其他工作树；用户数据默认保留。若提供删除数据选项，必须由用户明确选择。

### 9. 桌面操作与稳定性

- 增加托盘/菜单栏操作，至少包括显示窗口、打开设置和退出。按平台约定提供窗口关闭设置，默认值及首次行为清晰；Linux 环境没有托盘时禁用不可恢复的隐藏行为并保留窗口/菜单退出入口。
- 开机启动由用户自愿开启，默认关闭；后台启动时不无故弹出主窗口。
- 窗口位置、尺寸和最大化状态可恢复；多显示器变化后确保窗口仍可见。提供正常键盘焦点、快捷操作和高 DPI 适配。
- 扫描、刷新、导入导出和启动都保持界面可操作，显示真实进度或状态；支持合理重试，避免无响应或无限等待。
- 不通过增加冗余标签或说明掩盖交互问题；优先让主要操作和当前状态清楚。
- 以同一组代表性日志记录现有程序与客户端的冷启动、再次打开、列表滚动和空闲 CPU/内存数据，消除明显退化；具体优化以测量结果为依据。
- 睡眠唤醒、日志持续写入、后台服务异常退出后的恢复和长时间运行均需实际验证。

## 阶段四：更新与三端交付验证

### 10. 版本更新和分发

- 客户端与后台程序作为同一版本整体升级，避免界面与统计程序错配；应用自身负责安装版本更新，不依赖任何 Skill。
- 更新清单明确 OS、架构和安装渠道，不能把 Intel 与 Apple Silicon 或不同平台制品混用。AppImage 和直接安装的 Windows/macOS 应用可使用应用内更新；`.deb` 按包管理器或重新安装的渠道更新，应用内提供相应提示，不擅自使用 root 替换包管理器拥有的文件，也不让两个更新器争夺同一安装。
- 实现检查更新、版本说明、下载进度、由用户触发安装及重启。无网络、更新失败或下载被中断时，当前已安装版本应仍然可用。
- 使用签名验证更新来源，不能将 SHA256 校验等同于发行者签名。保护签名密钥，不在仓库、日志或客户端中放私钥。
- 升级协调退出本应用进程；配置、设备身份和导入快照保留。准备可验证的失败恢复与回退策略，涉及配置格式升级时避免旧版本静默损坏数据。
- 准备 Windows 应用签名、macOS 应用及辅助程序签名/公证的配置和验证流程；更新制品签名单独管理。没有用户提供的发行签名资源时先完成开发测试包与流水线，明确缺口，不声称已完成正式可信发行。macOS ad-hoc 开发签名不能当作已完成 Developer ID 签名及公证。
- 自动更新可先用本地或测试发布源完成端到端验证；公开发布及证书购买仍是独立外部动作。
- 提供安装包路径、版本及校验信息、用户使用说明、已验证系统环境和已知限制。客户端完整交付验收与基础原型验收分别记录，不能用原型成功替代安装与更新验收。

### 11. 三端构建与验收环境

- 复用现有原生 CI 的 Windows x64、macOS Intel/Apple Silicon、Linux x64 平台思路，增加桌面依赖、各平台打包和安装烟测；保持四种架构的服务与客户端匹配。
- Windows 使用 Windows 构建/运行环境；macOS 使用 macOS runner 或开发机；Linux 使用带所需依赖的 Linux 构建环境和真实图形会话。不能把在 Windows 上生成某个目标文件视为该系统已运行验证。
- 尽早确认 macOS 构建及桌面验证资源。可用 runner 能做构建和部分自动化，不等于已验收 Dock、系统文件对话框、安装、签名和更新；缺少环境时报告待验证项并继续其他可完成工作，不能无证据宣布三端完成。
- 在依赖版本支持时，评估 WebdriverIO Tauri 的 embedded WebDriver 做跨平台端到端测试；平台原生菜单、安装和系统行为另外验证。测试驱动和测试控制能力只进入测试构建，不随正式客户端暴露。
- 各平台记录构建、服务启动、GUI、安装、更新、签名的独立状态和证据，失败可定位到具体平台；不能用一个平台的通过覆盖其他平台。

## 可选的 Agensi 适配边界

- Agensi Skill 是操作指引，通过本地命令发现和控制已安装的应用；它不依赖自己已经保存成某个本地 Skill 目录。
- 客户端安装资源、用户数据和 Skill 分开管理；删除 Skill 不删除客户端数据。
- 协议兼容性与应用版本分开表达，避免每次 Skill 文案更新都要求更换二进制。
- 客户端安装版本由客户端更新机制管理，Skill 不直接覆盖其后台程序。
- 该适配不属于任何桌面端可用性的发布门槛；Agensi 尚未接入时，安装、使用、升级和自动化命令也必须独立工作。
- 不因为预留接口而自建平台专用 MCP 服务，不接入 Agensi 账号、支付或授权，不上传本地日志；专用 Skill 和商品提交在用户要求时单独实施。
- 平台外部程序安装与收费规则只约束平台适配包和上架承诺。届时重新核对条款并验证审核，不把这些限制写入客户端功能、独立安装分发或商业模式；若不适合则不接入。

## 建议实施顺序

1. 保留本计划和已有改动，在现有工作树同步最新 `origin/main`；阅读更新后的 AGENTS/UI 契约及有效设计参考，确认三端工具链、验证环境、其他运行服务和隔离目录。先跑相关基线检查，明确首批 OS/架构支持表。
2. 实现共享实例管理与就绪握手，接入现有启动器；按平台验证独立端口、复用、并发启动和安全退出。
3. 添加共用的 Tauri 宿主和四种架构构建矩阵，分别验证辅助程序定位、窗口、聚焦及退出，优先让三端都显示真实看板；完善长期设置存储。
4. 在三端验证原型日常操作、性能和故障恢复，按证据调整架构；完善通用本地命令，保持现有入口可用。
5. 生成三端交付包，完善首次启动、来源选择、原生文件操作、托盘/菜单栏、关闭行为及可选开机启动，采用平台适配而非 Windows 全量做完后再移植。
6. 分渠道实现并验证整体更新、数据保留和失败恢复，准备签名/公证及发布流水线；在对应系统完成安装、升级和移除验证。
7. 完成三端客户端验收和文档。每个阶段均交付可运行结果；原型完成后继续推进其余客户端阶段，不能因阶段划分或某一端完成就自行结束整个任务。
8. 最终使用最新构建重新启动各验证环境中的隔离实例，对照该平台二进制的 build ID，交付三端制品、可访问的实际 URL、分平台验证结果和限制；平台间不要求 build ID 完全相同。
9. Agensi 适配在客户端体验稳定且用户需要时单独开展，不阻塞客户端交付。

## 验证策略

- 对实例归属、状态迁移、并发启动、损坏记录、未知进程保护、JSON 错误协议和设置保存失败做有意义的自动化测试。
- 用虚构的最小 Codex 日志验证摘要数字、时区日期边界、完整/脱敏快照及重新导入；不要只断言命令退出成功。
- 使用三端真实系统 WebView 验证窗口和现有交互；浏览器通过不能替代桌面端到端验证。图形会话、系统菜单/对话框和安装升级分别记录，不能把无界面构建测试称为完整 GUI 验收。
- 同一组端到端核心用例在三端运行；冻结并记录测试依赖与 OS/WebView 版本。测试专用嵌入式 WebDriver 或控制插件应通过 feature/测试配置与生产构建隔离，不能让测试接口进入发行制品。
- 以最新主线的 `tooltip.test.ts` 和 UI 契约为基线验证提示框定位、翻转和边界，不从历史 CSS 或原始设计提示词另写一套规则。自动化位置测试不能代替真实 WebView 里的层级、键盘和视觉验证。
- 按 UI 契约检查被修改控件的默认、hover、focus、pressed、disabled 状态；提示框验证截图必须展示提示已打开，并覆盖窄窗口及必要的模态弹窗场景，保存在 `output/verification/`，不提交临时截图。
- 运行与修改相关的 Rust 格式化、clippy、workspace 测试、前端 check/测试及发布或安全测试。桌面依赖若不适用于无桌面环境，CI 使用清楚的目标/feature 划分。
- 现有 `tools/verify_native.mjs` 固定使用 8765，并有替换默认服务的选项；不可对用户已有实例直接执行。应先使验证器支持隔离地址，或新增针对新运行协议的隔离测试，再决定安全的兼容回归方式。
- 所有运行验证使用本工作树独立状态目录，不把临时快照、真实日志、截图、令牌、运行记录或构建产物加入 Git。

## 独立扩展路线

Windows、macOS、Linux 三端实现及验收、各自交付包、托盘/菜单栏、可选开机启动和更新已纳入本计划，不再排除。以下能力按产品需求独立扩展，不影响三端首批范围的交付：

- 更多处理器架构、Linux 发行版/包格式与系统应用商店；macOS Universal 合包可在两个独立架构交付稳定后再评估。
- Agensi 或其他市场的适配包、商品与审核：依附通用自动化接口，可选择接入或不接入。
- 更完整的 WSL 来源整合、多设备自动同步等产品能力：按真实用户需求决定优先级，独立于 Agensi。
